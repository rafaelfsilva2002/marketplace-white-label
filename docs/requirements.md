# Requisitos do Sistema - Marketplace White-Label Multi-tenant SaaS

> **Stack**: NestJS + Drizzle + PostgreSQL + Redis + Next.js 14 + Turborepo + pnpm + Stripe Connect + Algolia + Crypto + AI Gateway
> **Prioridades**: P1 (Obrigatoria), P2 (Importante), P3 (Desejavel)
> **Fases**: 0 (Alicerce), 1 (MVP), 2 (Monetizacao), 3 (Enterprise), 4 (AI-Native)

## FIN -- Financeiro

| ID | Titulo | Descricao | Criterio de Aceitacao | Prioridade | Fase |
|----|--------|-----------|----------------------|------------|------|
| FIN-001 | Saldo derivado de ledger entries | O saldo de qualquer wallet DEVE ser derivado exclusivamente da soma (`SUM`) de `ledger_entries`. Nao e permitido armazenar saldo como campo separado. Isso garante que o saldo e sempre consistente com o historico de transacoes. | 1. Consulta de saldo executa `SELECT SUM(amount) FROM ledger_entries WHERE account_id = ? AND tenant_id = ?`. 2. Nao existe coluna `balance` em nenhuma tabela. 3. Testes validam que saldo apos sequencia de operacoes (credito, debito, reembolso) e consistente. 4. Performance aceitavel com indice em `(tenant_id, account_id)`. | P1 | 2 |
| FIN-002 | Imutabilidade de ledger entries | Registros na tabela `ledger_entries` sao imutaveis. Nenhuma operacao de UPDATE ou DELETE e permitida. Correcoes sao feitas via lancamentos compensatorios. | 1. Trigger ou constraint impede UPDATE e DELETE na tabela `ledger_entries`. 2. Tentativa de UPDATE/DELETE resulta em erro do banco. 3. Campo `entry_type` distingue entre CREDIT, DEBIT, REFUND, COMPENSATION. 4. Audit trail completo de todas as entradas. | P1 | 2 |
| FIN-003 | Chave de idempotencia em operacoes financeiras | Toda operacao financeira (pagamento, saque, reembolso) DEVE aceitar e validar uma chave de idempotencia (`Idempotency-Key`). Requisicoes duplicadas com a mesma chave DEVEM retornar o resultado original sem executar a operacao novamente. | 1. Header `Idempotency-Key` obrigatorio em endpoints financeiros. 2. Tabela `idempotency_keys` armazena hash da chave, resultado e TTL. 3. Requisicao duplicada retorna HTTP 200 com resultado original. 4. TTL padrao de 24 horas para chaves. 5. Testes de concorrencia confirmam que operacao executa apenas uma vez. | P1 | 2 |
| FIN-004 | Atomicidade de transacoes financeiras | Operacoes financeiras compostas (debito + credito + comissao) DEVEM ser atomicas: ou todas as entradas do ledger sao criadas, ou nenhuma e. Falha parcial NAO e aceitavel. | 1. Transacoes financeiras usam `BEGIN ... COMMIT` no PostgreSQL. 2. Qualquer erro faz ROLLBACK de todas as entradas do ledger. 3. Testes simulam falha parcial e verificam que nenhuma entrada foi persistida. 4. Lock otimista ou pessimista previne race conditions em operacoes concorrentes na mesma wallet. | P1 | 2 |
| FIN-005 | Reembolsos como lancamentos compensatorios | Reembolsos NUNCA deletam ou alteram a transacao original. Em vez disso, geram lancamentos compensatorios no ledger que anulam o valor. Saldo apos reembolso total retorna ao valor pre-transacao. 4. Reembolso parcial e suportado. 5. Evento `payment.refunded.v1` e publicado. | P1 | 2 |
| FIN-006 | Suporte a multiplas moedas | O sistema DEVE suportar operacoes em multiplas moedas: BRL (Real), USD (Dolar), USDC (stablecoin). Cada ledger entry possui campo `currency`. Nao e permitido misturar moedas em uma mesma transacao atomica. 4. Taxas de conversao sao informativas; o sistema nao realiza cambio automatico. | P2 | 2 |
| FIN-007 | Comissao do marketplace configuravel por tenant | Cada tenant DEVE ter uma taxa de comissao configuravel (`commission_rate`) que e aplicada automaticamente em cada transacao. Ledger entry separada para comissao. 4. Dashboard exibe comissoes acumuladas por periodo. 5. Alteracao de taxa afeta apenas transacoes futuras. | P1 | 2 |

## EVT -- Eventos

| ID | Titulo | Descricao | Criterio de Aceitacao | Prioridade | Fase |
|----|--------|-----------|----------------------|------------|------|
| EVT-001 | Envelope padrao de eventos | Todo evento publicado DEVE seguir um envelope padrao com campos obrigatorios: `id` (UUID), `type` (string qualificada), `version` (semver), `tenantId`, `timestamp` (ISO 8601), `correlationId`, `payload`. Schema e validado via JSON Schema no CI. | 1. Eventos que nao conformam ao schema sao rejeitados na publicacao. 2. CI valida schemas de eventos contra o envelope padrao. 3. | EVT-002 | Outbox Pattern para publicacao apos commit | Eventos DEVEM ser publicados somente apos o commit da transacao de banco de dados. O padrao Outbox garante que evento e operacao sao atomicos: o evento e salvo na tabela `outbox` dentro da mesma transacao, e um dispatcher assincrono publica para o broker. | 1. Tabela `outbox` com campos: `id`, `tenant_id`, `event_type`, `payload`, `published_at`, `retry_count`. 2. Evento inserido na mesma transacao da operacao de dominio. 3. Dispatcher le eventos nao publicados e envia ao broker. 4. Apos publicacao confirmada, marca `published_at`. 5. Replay de eventos e possivel republicando da outbox. | P1 | 0 |
| EVT-003 | Retry com backoff exponencial | Eventos que falharem na publicacao ou processamento DEVEM ser reenviados com backoff exponencial. O numero maximo de tentativas e o intervalo base sao configuraveis. Apos esgotar tentativas, o evento vai para dead letter queue (DLQ). | 1. Formula: `delay = base * 2^attempt` (ex.: 1s, 2s, 4s, 8s...). 2. Maximo de tentativas configuravel (padrao: 5). 3. Eventos em DLQ sao alertados via metricas. 4. Operador pode reprocessar eventos da DLQ manualmente. | P1 | 0 |
| EVT-004 | Consumidores idempotentes | Todo consumidor de eventos DEVE ser idempotente: processar o mesmo evento mais de uma vez DEVE produzir o mesmo resultado. O consumidor DEVE verificar se o evento ja foi processado antes de executar a logica de negocio. | 1. Tabela `processed_events` com `event_id` como PK (por consumidor). 2. Antes de processar, verifica se `event_id` ja existe. 3. Se ja processado, retorna sucesso sem re-executar. 4. Testes enviam o mesmo evento duas vezes e verificam que o efeito ocorreu apenas uma vez. | P1 | 0 |
